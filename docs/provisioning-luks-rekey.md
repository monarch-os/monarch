# Provisioning disk ownership

`luks-rekey.sh` is sourced only by the packaged root provisioning executable. It is not the manual password-change API. While provisioning is pending, every non-owner slot (including a seller or recovery slot) is retired. Once the journal says `done`, an additional slot causes a failure rather than silent deletion.

The state directory and its ancestors must be root-owned and not group/world writable. `luks-key` and `luks-rekey-state` must be regular root-owned, single-link files with mode 0600. Before its local `luks-rekey.lock`, the engine acquires `/run/monarch-drive-password.lock`, shared with manual password changes and factory reset. A pending manual journal for the target UUID blocks provisioning. These locks do not serialize unrelated administrative cryptsetup operations; do not run those during provisioning.

All engine cryptsetup calls have a 120-second deadline, followed by forced termination after a five-second grace period. Expiration is an operation error, never a rejected-passphrase proof: it stops the transition without advancing to further revocations. The journal and staged key remain available for an explicit retry, including when a disk operation completed before its process timed out. This bounds the external cryptsetup wait, not total provisioning time or kernel uninterruptible I/O.

The journal is a strict six-field versioned record tied to the LUKS UUID, staged slot, reserved owner slot, phase and a SHA-256 keyboard-artifact fingerprint. That fingerprint covers console/locale configuration, the compiled console map and Unicode mode, the expected inclusion or omission of `vconsole.conf`, XKB and compose data, Plymouth keyboard libraries/binaries and the init/keymap/Plymouth/encrypt runtime scripts. It is never sourced. Complete replacement uses a private temporary file, file sync, rename and directory sync. Incomplete, unknown, duplicate and mismatched records stop the operation. Temporary journal files abandoned by a kill contain metadata only and are not read on retry.

- `staged`: a free owner slot has been reserved durably, before adding the owner secret. A crash after addition is resumed by proving the secret at that exact slot.
- `owner`: the owner's secret has been proved with a slot-specific passphrase test, excluding automatic/external tokens. Retries must use the same secret; they do not allocate another slot or change account passwords first.
- `boot`: current local Limine entries have matching BLAKE2b UKI hashes; each referenced UKI has been inspected for absent provisioning key/cmdline and matching console configuration. Only then are non-owner slots revoked, with sync and owner proof around retirement. A rebuild failure retains both enrolled secrets; it does not promise restoration of auto-unlock configuration. Retry provisioning or unlock with the owner password if a reboot is required.
- `done`: only the proved owner slot remains, boot is verified again, the staged key is removed and the directory synced. The journal remains until a subsequent reset replaces provisioning state. A retry after key removal needs only the owner secret. A changed keyboard causes a fresh build and verification before completion.

The provisioning form applies its selected keyboard before disk work. Disk work runs before account password changes, so a rejected retry cannot silently make login and disk passwords diverge. Unencrypted provisioning skips disk work unless residual staged-unlock or journal state exists.

## Reset and installer integration

`stage_current_owner_provisioning` copies `install/provisioning/luks-rekey.sh` alongside the current owner executable and setup form, using the same preflight and trusted package source. A factory snapshot can contain an older completed journal: reset removes `luks-rekey-state` and abandoned `.luks-rekey.*` metadata files from the **staged next root only**, before staging a new `luks-key`, rejecting symlinks in the cloned directory and its ancestors. Live state is never deleted. The engine initializes its own journal by proving the staged key against the target UUID; reset does not manufacture a completed phase. New deferred installers must ship the packaged helper as well.

## Validation boundaries

Tests simulate all disk/build operations and exercise real state publication, permissions checks, flock contention and UKI-verifier logic. They do not establish real cryptsetup, filesystem power-loss or firmware behavior. LUKS1 and LUKS2 dump formats and slot limits are parsed; actual compatibility of passphrase-only flags on both formats remains an installed-system acceptance requirement. Unsupported/failed commands stop before revocation.

## Keyboard artifacts, including non-Latin Plymouth fallback

The verifier preserves the policy implemented by `etc/mkinitcpio.conf.d/monarch_hooks.conf`, `monarch_vconsole.conf` and the repair introduced by commit `37bd688a0`. It evaluates trusted root mkinitcpio configuration with an inert `add_file` probe, including sorted administrator drop-ins. Latin-primary and KEYMAP-only configurations normally include `vconsole.conf`; non-Latin-primary configurations deliberately omit its implicit Plymouth copy. An explicit `FILES` inclusion still takes precedence. The extracted UKI must match the resulting choice exactly: omission is not an exemption from verification.

The console fallback is verified by reproducing mkinitcpio's `keymap` install-hook algorithm with `loadkeys -q [-u] KEYMAP -b`, which writes a compiled map to a private temporary file without loading it onto a console. The compiled bytes and empty `keymap.utf8` marker must match the UKI. Locale selects Unicode mode. During provisioning the persisted `KEYMAP` must also equal the form's selected map, which was applied with `loadkeys` before password collection. The extracted keymap, Plymouth and encrypt hooks must match their installed sources and execute before disk unlock; the verifier accounts for mkinitcpio forcing hook/init execute bits rather than incorrectly comparing their packaged 0644 modes.

Plymouth's graphical path needs more than a console file comparison. Its complete packaged XKB and X11 locale/compose trees must have the same file bytes and symlink inventory in the image, with no additional shadowing files. CachyOS ships `usr/share/X11/xkb` as a symlink to `xkeyboard-config-2`; that root is resolved only when it stays inside the system, while artifacts are compared under the logical `usr/share/X11/xkb` path the image actually contains. LUKS2 slot numbers are bounded numerically, so single-digit slots 4–9 are not mistaken for out-of-range values. The `plymouth`/`plymouthd` executables and the input implementation (`libply-splash-core.so.5` and `libxkbcommon.so.0`, including resolved targets) are also checked. Plymouth 26.134.222's `parse_vconsole_conf` calls `xkb_keymap_new_from_names` with default names when the file is omitted; older Plymouth 24 uses the console input path without an XKB layout. Thus an omitted file does **not** mean the selected non-Latin XKB layout should be reintroduced, nor that the image can omit the console fallback, XKB defaults or compose data. Both paths retain their existing Monarch policy; no new layout restriction or permissive fallback is introduced.

Keyboard/locale cmdline overrides, disabled hooks, image-local XKB/compose overrides, non-regular keymap/config files, wrong hook order, stale compiled maps or altered compose/library data stop the operation before revocation. Changed configuration, included console-map files, compose data or keyboard implementation bytes change the journal fingerprint and force a rebuilt and reverified image on retry, including after the provisional key was deleted.

These checks prove image artifacts against the selected console configuration and the installed Plymouth implementation, not physical keystrokes on every hardware keyboard or universal equivalence of Unicode compose sequences between Linux VT and XKB. Existing administrator-custom input implementations, kernel cmdline keyboard overrides and untested boot stacks require explicit review rather than silent acceptance. GitBook troubleshooting and disposable-VM boot acceptance remain follow-up work; no real console map, image build or VM was used in the tests.

Primary sources inspected: the repository's keyboard drop-ins and vconsole reconciler; installed mkinitcpio 42.2 `install/keymap`, `hooks/keymap`, `install/base`, `functions`, `init` and Plymouth install hook; upstream Plymouth 26.134.222 and 24.004.60 `ply-device-manager.c`/`ply-input-device.c` as distributed unchanged in the Debian `orig` source archives at `https://deb.debian.org/debian/pool/main/p/plymouth/`. No downloaded source was executed or built.

### Required runtime tools

Read-only manifest verification established the following dependency paths:

- `lsinitcpio` belongs to `mkinitcpio`. The `monarch` recipe depends on `limine-mkinitcpio-hook`, whose package manifest depends on `mkinitcpio`; the ISO target bootstrap also installs `mkinitcpio` explicitly. This tool is covered by the runtime dependency chain and fresh-install target list.
- `objcopy` belongs to `binutils`. The ISO's `builder/target-bootstrap.packages` installs `base-devel` before the runtime, and `base-devel` depends on `binutils`: fresh deferred installs following that target contract have the tool before provisioning. `install/monarch-other.packages` also includes `base-devel`, but that cache list alone is not proof of target installation.
- `install/monarch-base.packages` now requires `binutils` directly. The canonical required-package parser and reconciliation install it without relying on optional `base-devel`. `test/shell.d/package-manifest-test.sh` checks required-section membership and executes the existing reconciliation fixture against the full required set, including `binutils`.
- The integration coordinator supplies a direct runtime `binutils` dependency in the separately owned packaging change, based on the current `f5506c1` package line. The earlier observation against the old `59c9eac` recipe is historical, not a remaining packaging verdict for that assembled change. This worktree keeps the independent canonical required-manifest assertion. No package recipe was modified here.

Other existing runtime dependencies are reused: Python for the verifier and `kbd`/`loadkeys` for the same read-only compilation used by mkinitcpio (and the existing provisioning console setup). No new optional package bundle is required. Installed package metadata and the ISO bootstrap were inspected read-only; this is not a package transaction, a VM acceptance result or a claim that the coordinated packaging change is already published.
